# Day 99 — Technical Notes: Terraform, DynamoDB, IAM & Least Privilege

## 1. Mental model: four different objects

A **DynamoDB table** stores data. An **IAM role** is an assumable identity. An **IAM policy** defines allowed or denied API actions. A **role-policy attachment** associates the permission policy with the role. Creating these objects individually is not sufficient: a correct deployment must link them in the required way.

```text
EC2 service principal -> role trust policy -> nautilus-role
                                               |
                                        role-policy attachment
                                               |
                                        nautilus-readonly-policy
                                               |
                       GetItem / Scan / Query on nautilus-table ARN
```

The role is not attached to an EC2 instance by this challenge. An EC2 instance typically receives a role via an **IAM instance profile**, which is a separate resource. The trust relationship is necessary but insufficient to deliver usable credentials to an instance.

## 2. DynamoDB fundamentals

DynamoDB is AWS's fully managed NoSQL database service. Tables store **items** (roughly analogous to records), and items contain **attributes**. The table requires a primary key:

- **Partition key only:** Each item is uniquely identified by a hash/partition key such as `id`.
- **Composite key:** Partition key plus sort key; multiple items can share a partition-key value if sort-key values differ.

In this lab:

```hcl
resource "aws_dynamodb_table" "nautilus_table" {
  name         = var.KKE_TABLE_NAME
  billing_mode = "PAY_PER_REQUEST"
  hash_key     = "id"
  attribute {
    name = "id"
    type = "S"
  }
}
```

`S` means string; `N` means number; `B` means binary. The `attribute` configuration is for indexed/key attributes, not for declaring every application-level field. `PAY_PER_REQUEST` is on-demand capacity and does not require fixed RCU/WCU provisioning. It may be more expensive than provisioned capacity for some predictable high-volume workloads.

### GetItem vs Query vs Scan

| API | Access pattern | Cost/usage intuition |
|---|---|---|
| `GetItem` | Exact primary key lookup | Efficient single-item access |
| `Query` | Partition-key equality; optional sort-key range/prefix conditions | Efficient when query is aligned with key design |
| `Scan` | Iterate across the table or index | Can consume substantial capacity; avoid as default access pattern |

A `Query` against a GSI/LSI may also need permission on the index ARN; this lab creates no indexes and only authorizes the table ARN. `Scan`/`Query` are read operations but can expose many records and incur read charges.

## 3. IAM entities and policy types

- **User:** Long-lived identity, potentially with access keys (prefer roles when possible).
- **Group:** Collection of IAM users with shared policy attachments.
- **Role:** Assumable identity whose temporary credentials are provided by AWS STS.
- **Customer-managed policy:** Reusable standalone policy created and managed in an AWS account.
- **Inline policy:** Embedded directly within one user, group, or role.
- **Trust policy:** Resource-based policy on the role defining who may call `sts:AssumeRole`.
- **Permissions policy:** Identity-based policy defining what role credentials may do after assumption.

### Trust policy versus permissions policy

The trust policy (on `aws_iam_role`) allows `ec2.amazonaws.com` to assume the role. The identity permissions policy (on `aws_iam_policy`) grants DynamoDB operations to the assumed role. These are distinct evaluations. Permissions may further be limited by service control policies (SCPs), permissions boundaries, session policies, resource policies, or explicit denies.

## 4. IAM policy language

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": [
      "dynamodb:GetItem",
      "dynamodb:Scan",
      "dynamodb:Query"
    ],
    "Resource": "arn:aws:dynamodb:us-east-1:ACCOUNT_ID:table/nautilus-table"
  }]
}
```

`Version` specifies the IAM policy language version (not the Terraform or AWS provider version). `Effect` is `Allow` or `Deny`. `Action` names API permissions. `Resource` scopes the resources to which the action applies. `Condition` can impose additional constraints when supported.

**Least privilege:** Avoid `dynamodb:*` (grants more than read access) and `Resource = "*"` (grants across all applicable resources). Use the actual table ARN, generated by `aws_dynamodb_table.nautilus_table.arn`.

**Scope caveat:** The three API actions do not represent every possible DynamoDB read action. This is the exact minimal set requested; operations such as `DescribeTable` and `BatchGetItem` are not granted by this policy.

**Effective permission caveat:** The policy itself does not contain write permission. This does not imply the principal could never write if another attached policy granted that right. Evaluate effective permissions in production.

## 5. Terraform internals and HCL syntax

Terraform is declarative: configuration specifies the desired end state, and Terraform builds a dependency graph to plan changes. Providers are plugins implementing resource/data-source APIs. Terraform manages state to associate configuration addresses with remote resources.

- **Resource:** Creates or manages an object, e.g. `aws_dynamodb_table`.
- **Data source:** Reads an existing object without managing it.
- **Input variable:** External parameter to make configuration reusable.
- **Output:** Value exposed from the root module after planning/applying.
- **Local value:** Named expression within the configuration (`locals`).
- **Module:** Encapsulated collection of resources reusable by callers.

### Key Terraform commands

| Command | Responsibility |
|---|---|
| `terraform init` | Install providers/modules and initialize backend |
| `terraform fmt` | Standardize HCL formatting |
| `terraform validate` | Check configuration consistency, not AWS existence |
| `terraform plan` | Compare desired configuration against refreshed state and show changes |
| `terraform apply` | Execute an approved plan |
| `terraform output` | Print root module outputs |
| `terraform state list` | List tracked object addresses |

Always inspect planned changes. A successful `apply` is not the final check: perform a new `plan` and verify important resources from AWS when possible.

## 6. Inputs, tfvars, and outputs

```hcl
variable "KKE_TABLE_NAME" { type = string }
```

A value in `terraform.tfvars` is loaded automatically:

```hcl
KKE_TABLE_NAME = "nautilus-table"
```

Output example:

```hcl
output "kke_dynamodb_table" {
  value = aws_dynamodb_table.nautilus_table.name
}
```

The exact case of `KKE_TABLE_NAME` and `kke_dynamodb_table` matters. Plain `terraform.tfvars` is not always safe to commit: this lab file contains only non-secret names, but real variable files may contain sensitive tokens or passwords. Use `.gitignore`, secrets managers, and protected CI/CD variables accordingly.

## 7. `jsonencode()` and resource graph dependencies

The IAM policy object is defined in native HCL and passed to `jsonencode()`, which produces valid JSON. This avoids manual quoting and comma mistakes. The expression:

```hcl
Resource = aws_dynamodb_table.nautilus_table.arn
```

creates an **implicit dependency** from policy to DynamoDB table. The role-policy attachment references both `aws_iam_role.nautilus_role.name` and `aws_iam_policy.nautilus_readonly.arn`, so Terraform orders those resources correctly. You do not need an explicit `depends_on` for relationships represented by references.

## 8. Terraform state: accuracy, security, and drift

State is Terraform's record of managed infrastructure. Never hand-edit `terraform.tfstate`. Protect it: state may contain secrets or sensitive attributes. Production patterns include an appropriately controlled remote backend, encryption, access controls, state locking where supported, backup/retention, and separation by environment.

**Drift** occurs when an external change makes infrastructure differ from Terraform's desired configuration. `terraform plan` compares the configuration with refreshed remote state to propose reconciliation. A clean plan shows no actionable changes in modeled, non-ignored fields; it does not independently prove that external resources meet every business/security requirement.

Do not habitually use `lifecycle.ignore_changes` for security-sensitive IAM attributes: it can mask policy drift.

## 9. IAM security verification

Verify three things independently:

1. The DynamoDB table exists and is `ACTIVE`.
2. The policy's default version contains exactly `GetItem`, `Scan`, and `Query` on the specific table ARN.
3. The policy is attached to the intended role, and the role trust policy has the intended AWS service principal.

You can retrieve the full policy JSON through `aws iam get-policy-version`. IAM simulation APIs may not be supported by the KodeKloud AWS emulator; if they return “not implemented,” use direct resource inspection rather than treating it as a policy failure.

### Access model limitations

- EC2 instance roles normally require `aws_iam_instance_profile` and association with an EC2 instance (not part of this task).
- The role's trust principal must be selected based on the real consuming service in production. Here we use EC2 for the lab.
- IAM policies are global within an AWS account, while the DynamoDB table ARN includes a region.
- DynamoDB Scan/Query are read operations but may reveal sensitive data; least privilege should also consider application architecture, table designs, encryption, monitoring, and data classification.

## 10. Troubleshooting playbook

| Problem | Likely root cause | Correction |
|---|---|---|
| `InvalidKeySchema` | Missing partition key / attribute type | Add hash key `id` and string attribute |
| DynamoDB table `CREATING` | Asynchronous AWS provisioning | Check `describe-table` until `ACTIVE` |
| `MalformedPolicyDocument` | Invalid IAM action, ARN, or JSON | Check the generated `jsonencode()` output |
| IAM policy exists but unusable | Policy not attached to role | Create/check `aws_iam_role_policy_attachment` |
| `EntityAlreadyExists` | Name conflict in account | Inspect existing resource/state before importing or changing names |
| `No value for required variable` | Absent or misspelled tfvars entry | Check exact KKE variable names |
| `No changes` but access fails | Role trust/attachment/other IAM boundaries | Inspect both role trust and all effective permissions |
| IAM simulator `NotImplemented` | Sandbox API limitation | Use policy version and attachment inspection |

## 11. Production hardening recommendations

1. Trust only the intended service/identity, not broad arbitrary principals.
2. Grant the narrowest DynamoDB API actions and resource ARNs possible.
3. Attach role to workloads with temporary credentials, not embedded static keys.
4. Consider VPC endpoints for private DynamoDB connectivity when appropriate.
5. Encrypt state and restrict access to remote backends.
6. Version and review IAM policy changes in pull requests; run Terraform plan in CI.
7. Use CloudTrail, CloudWatch and IAM Access Analyzer for auditing.
8. Keep production variables and account IDs out of public repositories when sensitive.

## 12. Interview questions with short answers

**1. What is DynamoDB?** A managed key-value/document NoSQL database service on AWS.

**2. What is a DynamoDB partition key?** The key attribute used to distribute and identify items; it can stand alone or combine with a sort key.

**3. What does `PAY_PER_REQUEST` mean?** On-demand capacity billing without setting fixed provisioned RCUs/WCUs.

**4. GetItem vs Query?** GetItem looks up one item by full primary key; Query retrieves a set under a partition-key condition.

**5. Why can Scan be costly?** It reads through many items/segments and can consume substantial read capacity.

**6. What is an IAM role?** An assumable identity that provides temporary permissions to trusted principals.

**7. What is a trust policy?** The policy on a role specifying who may assume it.

**8. What is a permissions policy?** A policy controlling what API operations the authenticated principal may perform.

**9. Why attach a policy to a role?** Creating a standalone policy does not grant rights until attached to an applicable identity.

**10. What does `sts:AssumeRole` do?** Allows a trusted principal to obtain temporary role credentials.

**11. What is least privilege?** Grant only actions and resource scope necessary to perform a task.

**12. Why not use `Resource = "*"` here?** It would cover more DynamoDB resources than the one required table.

**13. Does this policy permit writing items?** No; it does not grant PutItem/UpdateItem/DeleteItem, although other policies might.

**14. Why use `jsonencode()`?** To transform HCL values into valid JSON and avoid hand-crafted string errors.

**15. What causes an implicit Terraform dependency?** A reference to another resource's attribute, such as `.arn`.

**16. What is Terraform state?** A mapping of configuration resources to managed remote objects and attributes.

**17. Why run `terraform plan` after apply?** To detect outstanding or drifted changes before submission/deployment signoff.

**18. Why avoid committing state?** It may expose secrets/sensitive metadata and produce conflicts between contributors.

**19. What is an IAM instance profile?** A container for an IAM role that can be associated with an EC2 instance.

**20. Is an IAM policy regional?** Customer-managed IAM policies are account-global; DynamoDB table ARNs remain region-specific.

**21. What if IAM simulation is unsupported?** Inspect attached policy version, trust relationship, and target ARN directly.

**22. What does an implicit deny mean?** No applicable policy allows the requested action; another allow could change effective access unless explicit deny/boundary prevents it.

**23. Can Query access a GSI with only table ARN permission?** Index access can require the index ARN too, depending on operation and index; this lab defines no indexes.

**24. Why use variables and outputs?** To parameterize infrastructure and expose selected deployment attributes without hardcoding them everywhere.

## 13. Summary

This challenge demonstrates an end-to-end, narrowly scoped IAM permission path from a trusted AWS service to a role and then to one DynamoDB table. The main insight: **trust, permission scope, and resource attachment must all be correct**. Terraform's graph makes deployment repeatable; AWS-side checks confirm the intended security posture.
